## 2. Check of the Builder's Claim on F7

**The builder's claim holds on F7's scenarios.**

- **Why neither loader fails on F7's scenario:** Both PyArrow's `ParquetFile.schema_arrow` (`FromParquetSchema` / `ApplyOriginalMetadata`) and Rust `parquet` `60.0.0`'s [`ArrowReaderMetadata::load`](kernel/mm/src/resolve.rs#L251) (`parquet::arrow::schema::parquet_to_arrow_schema_and_fields`) derive each root field from the Parquet physical/logical schema and treat `ARROW:schema` as an optional type hint (`Option<&Field>`). When a hint has an incompatible kind—such as `Struct` over physical `Int64` (`convert_primitive`) or `Int64` over physical `List` (`visit_list_with_item`)—both readers ignore the hint and keep the Parquet-derived Arrow type without raising an error.
- **Why our earlier suggested fix would have violated the spec:** Passing `ArrowReaderOptions::new().with_skip_arrow_metadata(true)` in [`Footer::read`](kernel/mm/src/resolve.rs#L251) would have ignored `ARROW:schema` on *declared* columns too, violating [SOURCES.md §2](kernel/SOURCES.md#L106-L108) (*"A column's type is its Arrow type as its file states it: the embedded Arrow schema (`ARROW:schema`) where present, else the Arrow type its Parquet physical and logical types map to"*)—for instance, decoding a declared `Dictionary(Int32, Utf8)` column in `ARROW:schema` as plain `Utf8` (a valid string cell) instead of `Dictionary` (not a cell).
- **Technical boundary (non-outcome-changing):** In `parquet` `60.0.0`, `parquet::arrow::schema::complex::Visitor::visit_struct` *does* return `ParquetError::ArrowError("Incompatible arrow schema, expected M struct fields got N")` if an undeclared column is simultaneously a Parquet `Struct` group and an `ARROW:schema` `Struct` with a different child-field count (hand-forged self-contradictory `ARROW:schema`), whereas PyArrow falls back to the Parquet struct. No Parquet writer emits such a file and no C7.6 or judged path can trigger it; leaving [`Footer`](ingest/resolve.py#L84-L106) and [`Footer::read`](kernel/mm/src/resolve.rs#L248-L274) unchanged is the right call.

     2. `recorded := known` and `key := int! r[2]!` (`e.event`, i.e., `slot`), ignoring `r[5]` (`e.recorded`) and `r[6]` (`e.key`) on event ties;
     3. `final := true` on every exported record—so if any key has $\ge 2$ delivered revisions (even without a retraction), `mmdump` exports all of them and [`Ctx.admissible`](reference/lean/Ref/Sim.lean#L444-L450) (`keys.eraseDups.length == keys.length`) aborts `refmm run` with `R_BINDING` while `mm` runs.
     All three will naturally be resolved when Stage 7 replaces `mmdump` / updates `Main.lean` for C7.7's revision-carrying market exporter (already noted in [PROGRESS.md](PROGRESS.md#L29) and [decisions.md](audit/decisions.md#L820-L821)).

## 5. Remaining or New Findings (Ranked by Severity)

### NF1 (Low): C7.6 Named Test 1's second positive control tests old-revision fallback rather than a retraction's stored values, and Python's observation projection lives in test glue

- **Place:** [`stored_on_retractions`](kernel/tests/rules/test_suite.py#L123-L129) and [`test_the_observation_comparison_catches_its_controls`](kernel/tests/rules/test_suite.py#L137-L147) in [test_suite.py](kernel/tests/rules/test_suite.py); [`listing`](kernel/tests/rules/loaders.py#L60-L71), [`observations`](kernel/tests/rules/loaders.py#L74-L77), and [`delivery`](kernel/tests/rules/loaders.py#L84-L90) in [loaders.py](kernel/tests/rules/loaders.py).
- **Defect:**
  1. [criteria.md](audit/criteria.md#L1129-L1130) specifies Named Test 1's three positive controls as *"a loader delivering the final revision's values on every entry, **a retraction's stored values**, or every entry as final, fails it."* [`stored_on_retractions`](kernel/tests/rules/test_suite.py#L123-L129) instead substitutes `before[tuple(o[:3])][7:9]` (*"those of the entry before it"*—i.e., old-revision fallback), ignoring the retracting revision's own stored cells in `c["rows"]`.
  2. [criteria.md](audit/criteria.md#L1100-L1101) requires both `ingest/resolve.py` and `kernel/mm/src/resolve.rs` to produce §7's result and observations *"from its production resolver, never from a second path."* Rust implements [`Resolved::listing`](kernel/mm/src/resolve.rs#L696-L722) and [`Resolved::observations`](kernel/mm/src/resolve.rs#L726-L753) in production code, whereas Python builds both in the test adapter [loaders.py](kernel/tests/rules/loaders.py#L67-L90), where `None if e.retraction` ([loaders.py](kernel/tests/rules/loaders.py#L68)) and `None if retraction` ([loaders.py](kernel/tests/rules/loaders.py#L87)) re-mask `e.cells` on retractions inside test code.
- **Scenario:**
  1. Suppose a suite's retractions were all bare tombstones storing no value/role columns (`{"coin": "BTC", "eventTime": E}`, `tombstone=True`), or a key's prior entry had undefined values (`[None]`) while its retracting revision stored `close: 1.0`. On bare tombstones, a loader bug that delivers a retraction's stored values (such as omitting `if e.retraction` in [`Resolved::observations`](kernel/mm/src/resolve.rs#L733-L736)) delivers `[None]` and passes the Lean comparison undetected, yet `stored_on_retractions` copies `before`'s non-null values and still passes `caught >= 10`. Conversely, on a `[None] -> retract(close=1.0)` key, `stored_on_retractions` copies `[None]` and misses the case.
  2. If [`resolve.timeline`](ingest/resolve.py#L298-L299) regressed to storing `r.cells` instead of `None` on a retraction `Entry`, [`loaders.listing`](kernel/tests/rules/loaders.py#L68)'s `None if e.retraction` check in test code would silently mask the regression during C7.6's suite run.
- **Outcome:** Production code in [`ingest/resolve.py`](ingest/resolve.py#L298-L299), [`Store.entries`](ingest/store.py#L184), and [`kernel/mm/src/resolve.rs`](kernel/mm/src/resolve.rs#L733-L746) is unaffected and handles retractions properly, and the frozen B3 suite already has $\ge 11$ `HAND` cases ([resolver_suite.py](kernel/tests/rules/resolver_suite.py#L182-L192), [#L333-L357](kernel/tests/rules/resolver_suite.py#L333-L357)) plus generated cases whose retracting revisions store non-null numeric cells. However, Named Test 1's second control does not currently test the defect class named in C7.6, and Python's observation formatting sits in test glue rather than `ingest/resolve.py`.
- **Fix:**
  1. In [`test_suite.py`](kernel/tests/rules/test_suite.py#L123-L147), pass `(c, lean["result"], lean["observations"])` to the controls and implement `stored_on_retractions` by looking up the retracting revision's own `cells` via [`resolver_suite.stored`](kernel/tests/rules/resolver_suite.py#L76-L81) (decoding `[lean_check.bits(cells.get(v)) for v in s["values"]]` and any decodable role payload when `o[5]` is `True`).
  2. Move `listing` and `observations` into [`ingest/resolve.py`](ingest/resolve.py) (matching [`Resolved::listing`](kernel/mm/src/resolve.rs#L696) and [`Resolved::observations`](kernel/mm/src/resolve.rs#L726)), deriving `cells` / `values` from `e.cells is None` rather than re-masking on `e.retraction` in [`loaders.py`](kernel/tests/rules/loaders.py).

## 6. Notes (Cannot Change an Outcome)

1. **`Store._frame` empty-`tables` schema fallback ([`ingest/store.py`](ingest/store.py#L165-L170)):** When *zero* rows in a dataset have `fetchedAt <= version` (`tables` is `[]`, as in [`test_as_of_never_leaks`](ingest/tests/test_store.py#L73-L80) at `version=50`), `Store._frame` synthesizes its 0-row DataFrame's column names and types from `footers` because an undecorated `Store` has no external source declaration on disk. Adding a post-`version` file with a new column therefore adds that column to an all-empty `Store.as_of` schema (whereas before the first file existed, `Store._resolved` raised `FileNotFoundError`). Whenever at least one pre-`version` row exists—and always in [`resolve.resolve`](ingest/resolve.py#L239) and `mm`, where declarations are explicit—post-`version` files cannot affect columns or types.
2. **Fixture perturbation coverage in [`noninterference.rs`](kernel/mm/tests/noninterference.rs#L118-L125):** [`PROGRAM`](kernel/mm/tests/noninterference.rs#L21-L32) reads all 7 venue inputs, and [`write_bars`](kernel/mm/tests/common/store.rs#L108-L111) varies `open`, `high`, `low`, and `close` with `close * 1.2`, while `volume` (`1.0`) and `premium` (`0.0` in [`write_funding`](kernel/mm/tests/common/store.rs#L87)) stay constant across the baseline and `late` stores. Because [`market::load`](kernel/mm/src/market.rs#L275-L307) attaches a single `known` timestamp per `Funding` and `Bar` record (directly mutated by `S2` and `S3`), no record-level read-ahead can affect `volume` or `premium` alone, though varying them too in `early_bars`/`early_funding` would cost one line if columns are ever split in Slices 3–4.
