#### 2. [High] The Parquet-vs-Arrow schema name rule is undefined on nested columns (`List`, `Struct`) and column order, breaking on Test 3's own `List` variant, Test 2, and C7.6's Parquet image

- **Exact place:** [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L147-L148) (`SOURCES.md` §2); [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L26-L27), [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L53-L60), and [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L68-L70); [`VARIANTS`](ingest/tests/test_store.py#L184-L185) and [`staged`](ingest/tests/test_store.py#L188-L202) in [test_store.py](ingest/tests/test_store.py).
- **The defect:** Round 8 marks a Parquet file invalid *"whatever V"* — and in Named Test 3 rejects it in the **footer schema check before the holdout check** — if *"its embedded Arrow schema or Parquet schema names one column twice, or whose two schemas disagree in their names"*.
  1. **Leaf columns vs. root-group fields:** In Parquet, `FileMetaData.schema` is a tree. Standard APIs for "the Parquet schema's names" (`pyarrow.parquet.ParquetFile(f).schema.names` in Python; `SchemaDescriptor::columns()` in Rust `parquet`) return **leaf** column names (`"item"` or `"element"` for a `List`; child field names for a `Struct`), whereas `ARROW:schema` and the Parquet root group's direct children list **top-level** column names (`"rate"`).
  2. **Set vs. ordered list of names:** The text does not specify whether *"disagree in their names"* compares the **ordered list** of top-level names or only the **set** of names (even though Arrow-rs maps `ARROW:schema` fields positionally onto Parquet root fields).
- **Concrete scenario:**
  - **Nested columns (exercised by `test_store.py` as written):** In [`VARIANTS`](ingest/tests/test_store.py#L185)'s fourth entry `({"rate": [[1.0, 2.0]]}, False)`, `1.parquet`'s embedded `ARROW:schema` has names `['coin', 'eventTime', 'rate', 'fetchedAt', 'source', 'hash', 'tombstone']`, while `pq.ParquetFile("1.parquet").schema.names` (and Rust `schema_descr().columns()`) has `'item'`/`'element'` in place of `'rate'`. Implementation A (comparing `ParquetFile.schema.names` / `schema_descr().columns()` to `ARROW:schema` names) rejects `1.parquet` in the **footer schema check** as `"invalid dataset"` on `VARIANTS[3]` while refusing `VARIANTS[0..2, 4]` as `"holdout crossing"` — **failing Test 3**! Implementation A likewise rejects undeclared `List`/`Struct` columns in Test 2 (contradicting [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L54-L55): *"in an undeclared column are never read"*) and rejects any C7.6 Parquet image with two non-cell declared values written as `List` columns ([c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L26-L27), duplicate leaf `'item'`). Implementation B (comparing top-level root children) accepts them and passes.
  - **Permuted order:** On a file whose Parquet root group lists `[coin, eventTime, fetchedAt, close]` and whose `ARROW:schema` lists `[coin, eventTime, close, fetchedAt]`, an implementation checking name sets accepts it (or misbinds columns positionally), while one checking ordered top-level name lists rejects it as `"INVALID"`.
- **Outcome it could change:** Changes C7.6's verdict on Named Test 2, Named Test 3, and non-cell Parquet images, and causes `mm` and Python to disagree on dataset validity.
- **Design change or wording fix:** **Design / specification change.** Define the check explicitly on the **ordered list of direct children of the Parquet root schema group** and the **ordered list of top-level fields of `ARROW:schema`** (when present): neither list may repeat a name, and the two ordered lists must be equal (with declared/metadata columns' `ARROW:schema` types compatible with their Parquet columns, and undeclared columns' subtrees ignored).

#### 3. [Medium] `c76-revision.md` puts `"the event-time column present"` in footer schema checks, contradicting `RULES.md` §6 and `SOURCES.md` §2

- **Exact place:** [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L23-L33) and [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L58-L65), vs. [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L27-L30), [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L47-L48), and [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L145-L148).
- **The defect:** [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L58-L60) states: *"first the schema checks, on each file's footer: `fetchedAt`'s type, `tombstone`'s type, no column named twice ... and **the event-time column present** ... Then the holdout check"*.
  In [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L145-L148) (`SOURCES.md` §2), however, a missing event-time column is **not** a file-level ("whatever V") schema invalidity: *"An absent column is null"* ([rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L47-L48)), *"revisions fetched after V are not examined"* ([rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L27)), and under a holdout bound a row with a null event time must be refused as *"the holdout check cannot be made", not dataset invalidity* ([c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L63-L65)).
- **Concrete scenario:**
  1. **Search mode (`holdout_start` set):** `1.parquet` has 1 row with `fetchedAt = 200 > V = 100`, `coin = "A"`, `rate = 1.0`, and **no `eventTime` column** (or has **0 rows** and no `eventTime` column). Loader A (following [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L58-L60)) rejects the footer before the holdout check as **dataset invalidity** (`R_BINDING` at admission stage 6 in `mm`), even on the 0-row file. Loader B (following [rules-revision.md](audit/stage7/b3-draft/rules-revision.md#L47-L48) and [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L63-L65)) treats the 1-row file's absent `eventTime` as `null` and refuses at stage 2 with **`"the holdout check cannot be made"`** (`R_HOLDOUT` at position 5 in `mm`), and admits the 0-row file.
  2. **Bound-less / holdout mode (`holdout_start = None`):** On the §7 case `rows = [rev("bars", 100, {"coin": "BTC", "eventTime": 36000000, "close": 1}), rev("bars", 200, {"coin": "BTC", "close": 2})]`, `version = 100`, Lean ([`resolveCase`](reference/lean/Main.lean#L494-L504)) and GPT ignore the post-$V$ row and **resolve** the store. Under C7.6's Parquet image ([c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L25): *"holding ... its declared members"*), `1.parquet` omits `eventTime`; a loader running [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L58-L60)'s footer schema checks rejects `1.parquet` as **`"INVALID"`**, disagreeing with Lean and GPT.
- **Outcome it could change:** Flips `mm`'s refusal code/stage (`R_BINDING` vs. `R_HOLDOUT`), Python's refusal cause, and C7.6's 4-way agreement (`"INVALID"` vs. resolved timeline) on post-$V$ or 0-row files lacking the event-time column.
- **Design change or wording fix:** **Design / specification change.** Remove `"and the event-time column present"` from the footer schema checks in [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L60) (and clarify in [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L25) whether absent declared members are omitted or written as `Double` null). In search mode, a file missing the event-time column with `num_rows > 0` in its footer has `null` event times and is refused by the holdout check with `"the holdout check cannot be made"`; a 0-row file or a post-$V$ file in bound-less mode is valid.

- **Exact place:** [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L63-L75); [`FIXTURES`](ingest/tests/test_store.py#L182-L183), [`VARIANTS`](ingest/tests/test_store.py#L184-L185), and [`holdout_check`](ingest/tests/test_store.py#L247-L253) in [test_store.py](ingest/tests/test_store.py).
- **The defect:**
  1. **Uncheckable `Int64` event times:** [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L63-L65) requires any event time outside `[−2^62, 2^62 − 1]` or null (*"in Parquet, a non-null Int64 in it"*) to trigger `"the holdout check cannot be made"`. Yet [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L74-L75) and [`FIXTURES`](ingest/tests/test_store.py#L183) test **only `Double`**. Demonstrating the gap, [test_store.py](ingest/tests/test_store.py#L249-L252)'s own reference [`holdout_check`](ingest/tests/test_store.py#L247-L253) checks only `dtype != pl.Int64` and `eventTime >= HOLDOUT_START` — missing both `Int64` nulls (dropped by `.filter(...)`) and out-of-range `Int64`s (`< -2**62` or `>= 2**62`, where `2**62` is also misclassified as a holdout crossing rather than uncheckable if `>= HOLDOUT_START` runs before the range check).
  2. **Null `fetchedAt` ordering:** [c76-revision.md](audit/stage7/b3-draft/c76-revision.md#L65-L66) specifies *"Everything else, a null `fetchedAt` included, is found after the check passes"*, yet [`VARIANTS`](ingest/tests/test_store.py#L184-L185) never varies `fetchedAt` (e.g., `Int64` `None`).
