## 1. D212, the horizon `floor_midnight(last_quote_universe − D_capture − 1 h)`

**What I accept.** Deleting the host wall clock from the pull's completeness argument is right, and the chain `t_0 = t_2 − D ≥ lq − D ≥ T + 1 h` is sound under three premises: every captured universe quote's venue stamp is at most the venue time at its receipt; `m_0` and `m_2` are one boot's `CLOCK_BOOTTIME`, which counts every second that passed; and settlements are indexed within the margin. Drift (20 to 500 ppm over at most 90 min, a few seconds at worst) is negligible. The file listing and length snapshots precede `m_2`, so nothing written after `t_2` enters `lq`. Under these premises, a stamp later than the capture's end cannot come from an honest line.

### F1.1 (design). One line moves the horizon without bound
- **What breaks.** `last_quote_universe` is a maximum over about two billion raw stamps, so the whole proof rests on the single largest one. Round 7's host-clock cap was also an upper bound on `T`; round 8 deleted it, and no upper bound remains.
- **Construction.** One `l2Book-fast` line of a universe coin, two-sided and not crossed, whose `time` is in the future: a venue node's clock error, a stamp in µs rather than ms after an API change, or a recorder bug. Say it reads 2030. Then `lq − D − 1 h` falls past `w_start + 730 d`, so `T = w_start + 730 d`.
  - Nothing feeds that line, since it is past `w_end`, but it has already set the horizon. The replay runs past the end of the record.
  - If a coin is held, its first hour after the pull's coverage has no row, and A9 aborts with `R_SETTLEMENT_MISSING`. That is an agreed abort, so `ended_study`.
  - If no coin is held, days with stale marks are published. Next month the real quotes of those days arrive, the prefix check diverges, and the study ends.
  - A smaller overshoot ends it the same way: at a 12:00 firing, a stamp about 13 h ahead suffices; at a retry firing near 23:00, about 2 h ahead.
- **Outcome.** The study ends at the capture after the line. CS2.2 is "not judged" if this falls before day 212, and CS2.1 is cut short, with every later day lost.
  - There is also a smaller path to a false discovery. On the overshoot day, the day's-end `account` row is computed at a stale mid-day mark. A rung-2 crossing there is a final "outgrew", and D215 keeps it after the divergence, so it is a look at a time the e-process was never defined at.
- **Cause and direction.** The statistic is not robust, which is a defect of the design. The quantity needed is a lower bound on the venue's time at `t_0` that no single line can inflate. Two shapes need no clock and no patch:
  - the minimum over universe coins of each coin's latest quote stamp, so that all 17 coins would need wild stamps (a quiet coin only holds the horizon back, which is conservative);
  - the pull's own coverage, `floor_midnight(min_c last_row_time_c + 1 h)`, which needs no `D`.

  Either also fixes F1.2 and F1.4. Choosing between them is the architect's call. My point is only that a maximum over raw stamps cannot be the witness.

  Two further points:
  - A maximum over all history also makes one wild stamp permanent: every later capture overshoots too.
  - The maximum needs a pass over every captured `l2Book-fast` frame before `start` can be given its horizon. A per-coin "last written" stamp needs only the tail of the open files.

### F1.2 (design). `T_k` can fall below `T_{k−1}`, and that ends a valid study
- **What breaks.** `T_k` is computed afresh at each capture from `(lq_k, D_k)`. `lq` is non-decreasing because files only grow, but `D` is not monotone: the pull from `w_start` grows by about 1.6 min a month, and 429 backoff varies it by up to the 90 min kill. Brief 4 never defines a replay whose horizon falls before `T_prev`. Its prefix check requires the rows up to `T_prev` byte for byte, and a shorter run lacks them, so it reads as "the record of a published day has changed", which gives `end_study`.
- **Construction.** The recorder stops, which brief 4 itself foresees about 2027-05-20 with the human's choice deferred. Its last universe quote is at 01:45 UTC on day `D`.
  - In month `k−1`, `D_{k−1} = 40 min`, so `lq − D − 1 h = 00:05` and `T_{k−1} = 00:00 D`, which is published.
  - In month `k`, `D_k = 46 min`, so `lq − D − 1 h = 23:59` on day `D−1` and `T_k = 00:00 (D−1)`.
  - The record has not changed, yet the replay is one day short. The study ends at `T* = T_k`, and a non-final "earned" on day `D−1` is withdrawn.
  - It follows with certainty whenever the recorder dies with `lq`'s time of day between `01:00 + D` at the death and `01:00 +` the largest `D` seen later. That band is about 30 min from the pull's growth alone, about a 2% chance per stop, and up to 90 min with 429 backoff, about 6%.
- **Outcome.** A valid published day is lost, a non-final "earned" can be withdrawn, and the study ends. A study that should have resumed when the human restored the volume does not resume. This changes CS2.1 and CS2.2 as judged.
- **Cause and direction.** This is a defect of the design: the derivation ignores what an earlier capture already proved. Capture `k−1` finished before capture `k`'s pull began (the lock and capture order guarantee it), so `t_0(k) ≥ t_2(k−1) ≥ lq_{k−1}`. The bound `max(lq_k − D_k, lq_{k−1})` makes `T` monotone by derivation, with no rule added. Separately, brief 4 must say what a run shorter than `T_prev` is. It cannot be a divergence.

### F1.3 (text, with a design premise). Where `D_capture` comes from
- **What breaks.** `D = m_2 − m_0` is meaningful only within one boot. VAULT.md has `mmvault funding` record its own `elapsed_ms` in `stop`, while `D_capture` spans pull plus snapshot. Neither text says that `m_0` and `m_2` are read in one process, on one host, in one boot (`/proc/sys/kernel/random/boot_id` recorded beside them). Neither checks `D ≥ 0` or `D ≤` the 90 min kill plus the snapshot time.
- **Construction.**
  - If the implementation reads `m_0` in the pull's pod and `m_2` in a capture step on another node, `D` is the difference of two uptimes. A negative `D` overshoots `T` by `|D|`, which then runs as in F1.1.
  - Separately, `CLOCK_BOOTTIME` does not advance while a hypervisor pauses a guest. If Step 1 ever runs in a VM, a pause during the pull understates `D` by the pause, and a pause longer than the margin overshoots `T` across a midnight whose 23:00 row was not pulled.
- **Outcome.** Any overshoot ends the study, as in F1.1.
- **Fix.** This is a defect of the text. Pin `boot_id` at both reads, refuse a capture whose two `boot_id`s differ or whose `D` lies outside `[0, 90 min + snapshot bound]`, and state "bare metal, or a guest whose monotonic clock advances during a pause" as a premise.

### F1.4 (design, through D211). A short page is taken for a complete coin
- **What breaks.** VAULT.md: "A coin's pull is complete at its first page under 500." The horizon's proof needs each coin's pull to reach the venue's `now`. Nothing checks that the last row of a "complete" coin is recent.
- **Construction.** The info server returns 499 rows on a page for any reason: a server-side row or time cap, a partial index, or a shard answering late. Every later row of that coin is missing from this pull. For a held coin, the first missing hour aborts the run and the study ends. For a coin not held, next month's pull holds the rows, the trace's `funding` rows differ, and the study ends.
- **Outcome.** As in F1.1. This is the same missing witness: with the coverage bound named in F1.1, a short page only holds the horizon back.

### Note N1.1. "Strictly one clock" overstates
Listings copies are timed and chosen by `recv`, the host clock (`KERNEL.md`, revised A18; wall 2). The claim is true of the horizon only. This changes no outcome, since round 7 already accepted the listing's timing as reported. It is a correction to the text.

## 2. D211: the pull from `w_start`, atomic staging, hash reuse, and 2-of-3

**What I accept.**
- Staging each pull and renaming it into place only when every coin has completed removes partial pulls and the `:07` race without any cross-pod lock.
- Reusing closed-file hashes is sound for the capture's own notion of "closed": a stream that ended cleanly, never appended again (`RECORDER.md`). A size check plus re-verification by the replay at read time is no weaker than hashing again, since rot is caught either way. Under either scheme, rot on a published day's bytes ends or halts the study unless a copy exists.
- The 2-of-3 rule gives no lever over which output wins. Outputs are sealed (only hash and status are logged), the build is deterministic, and a killed run retries to the same bytes. Choosing the third host cannot be aimed at a verdict nobody has seen. Its residue is the stated common-mode assumption.

### F2.1 (design). An agreed refusal has no state, so the study can stall silently
- **What breaks.** Round 8 sorts every attempt into "no output", which is transient and retried forever, or "an output", which is compared. The only refusal given a terminal state is `E_HASH` on two hosts. A deterministic refusal gives no output on every host, so it is retried forever. Examples:
  - `E_HEADER`, when no listings copy `≤ w_start` exists;
  - a coin-frame purity failure from a deterministic packer defect;
  - a malformed pinned frame.

  The capture has the same gap: "failing closed if an immutable file changed size" yields no `Capture_k`, and the hourly firing then fails forever (one way to reach this is F4.1).
- **Construction.** A deterministic packer defect puts one ETH line into frame `BTC` of an hour that both hosts packed alike. Every replay host refuses on purity, so there is no output. Step 2 retries; month 2's capture queues behind it, since Step 2 runs "the earliest capture not yet settled". Nothing settles, no `halt_*` is recorded, and the timer keeps firing.
- **Outcome.** CS2.1 to CS2.3 are never judged, and no state, report or halt says why. A human may notice, but nothing in the design will.
- **Fix.** The fault is in the state machine, not the text. Add a third class: the same refusal code from two distinct hosts is an agreed output, settled as `halt_refused(code)`. A capture whose immutability check fails is `halt_storage_corrupt`. Both stop the timer and appear in the report.

### F2.2 (design cost, unpriced). The pull from `w_start` lets any change to any historical row end the study
- **What breaks.** Round 7 re-read only new days, plus the daily job's 30-day pull. Round 8 re-reads every settlement since `w_start` each month. Any later difference in any such row has one of two effects:
  - a second settlement of one hour, which A18 rejects, so the run aborts at that hour;
  - a different payment, which makes the prefix diverge.

  Either way the study ends at the midnight before the earliest such hour. Placed-decimal equality absorbs trailing zeros, not values.
- **Construction.**
  - In month 14 the venue raises `fundingHistory`'s precision, serving 10 significant digits where it served 8. This changes the value of every old row.
  - Month 14's pull from `w_start` re-delivers day 1's hours with new values, the run aborts at the first held hour of day 1, and `T* = w_start`.
  - Every non-final "earned" is withdrawn. A final "outgrew" and a CS2.2 already judged stand.
  - Under round 7's pull the same change would have reached only rows from the last 30 days.
- **Outcome.** The whole study can be lost to one benign change of the venue's API. No false discovery is added.
- **Judgment.** This follows from "read the record as it is", which brief 4 defends as the price of not cutting. The report presents the pull from `w_start` as strictly stronger than `e691341` and never states this cost, which grows with every month run. I do not call it a defect. It is a trade the architect should price explicitly, and the human should hear it in plain words: a venue-side change to old funding rows ends the positive control. The exposure cannot be removed without keeping first readings of restated rows, which round 5 rejected. Both choices keep the 5% bound, since each reads one consistent record. So this is a choice of which record the claim is about, paid for in the study's survival, and it should be written down as one.

### Note N2.1. Durability of the rename
VAULT.md renames into `settled/funding/` but never says to `fsync` the destination directory before the capture lists it. On ext4's ordered journal, the capture's own commit makes the rename durable in practice. On another filesystem, a power cut between the rename and the directory flush, after a durable `Capture_k`, gives `E_HASH` on every host and so `halt_storage_corrupt`. Fix in one line of the spec.

### Note N2.2. Rate budget
The daily `settled` job (00:17) and the replay timer each pace at 750 weight/min, with no shared budget. When an hourly retry overlaps 00:17 the total is 1,500, above 1,200, so 429s fail the whole pull. Retries are hourly, so this costs only liveness.

## 3. D213: `RunInput_k = (Capture_k, State_{k−1})`

**What I accept.** Moving the prefix check, `T*`, the verdict carry-forward and the fee-schedule witness inside the compared output removes round 7's single-coordinator gap. The list of pinned files is complete for the data a run reads: registration, `State_{k−1}`, forward channels (packed or raw), listings, settled funding, all `mmvault` files, the fee-schedule copy, the vault's pre-2026-11-01 copy, and `D_capture`. Every one is verified in memory before it is decoded. The `(tid, oid)` fallback makes the order of unchainable fills a function of the record.

### F3.1 (text, with a design consequence). The protected-windows file is an input that `RunInput_k` does not pin
- **What breaks.** The windows file is compiled into the build. `study2 forward` accepts a build that differs from the registered one only by a release (brief 4, step 6), and then "reads the released days". So the set of days a run may read depends on which build the host has. That is not in `RunInput_k`, and step 7 depends on "the release of 2027-01-31" (brief 4, the order).
- **Construction.**
  - Month 1's capture is taken on 2027-02-01. Host A runs before the release commit lands and is rebuilt; host B runs after.
  - The vault's replay reads fills back to April 2026, through the window, and the engine refuses a protected date ("neither holds a date the engine refuses", CS2.3). On host A the window's fills fail their replay; host B reads them.
  - The outputs differ (layer 1's summary, and CS2.3's judging if day 61 falls in that month). The third host decides 2-of-3, and a healthy host is retired.
  - If a refusal surfaces instead as "no output", A retries until rebuilt, which is benign but undefined.
  - The same happens at any later release that touches what a run reads.
- **Outcome.** A healthy host is retired, or a run is refused forever, depending on how refusals are classed. Combined with F2.1, the study stalls or halts. No verdict is changed.
- **Fix, at the cause.** The protected windows in force are a capture input. `Capture_k` pins the windows file's hash, and a run refuses a build whose windows differ from the capture's. Step 1 does not capture while a date the run will read is still protected, so `R_PROTECTED` can never arise at run time. A release takes effect at the next capture. This also makes F2.1's agreed-refusal halt safe: no expected refusal remains.

### F3.2 (text). The host's environment is an unpinned input, and the 3-way halt makes it fatal
- **What breaks.** The compared output is "everything it computes from `RunInput_k`". A run also reads its process environment:
  - `TZ` and `/etc/localtime`, which matter wherever the report renders a time in local time or "EST";
  - the locale, through number or text formatting in OCaml or C;
  - `OCAMLRUNPARAM`, whose `R` randomizes `Hashtbl` iteration;
  - the CPU count, if any pool sizes itself from it.

  Under round 8's rule, three hosts that differ in any of these give three distinct outputs, and the study halts unconditionally.
- **Construction.** Three NixOS hosts, one with `time.timeZone = "America/New_York"`, and a report line written as "12:00 UTC (07:00 EST)" through `localtime`.
- **Outcome.** `halt_non_deterministic` on a correct build. CS2.1 to CS2.3 are not judged.
- **Fix.** The runner executes `study2 forward` under a fixed, recorded environment (`env -i`, `TZ=UTC`, `LC_ALL=C`, no `OCAMLRUNPARAM`, a fixed pool size). A test runs two hosts whose `TZ`, locale, `OCAMLRUNPARAM=R` and core counts differ and requires byte-identical outputs.

### Note N3.1. The firing log
The report "lists each firing whose pull failed", but "the operational run/firing log" is excluded from the comparison, so a faulty host could write a wrong list. It judges nothing. If its source, the pinned `settled/events` files, is pinned, it can simply be compared.

## 4. D216: closed-hour per-coin seekable packs

**What I accept.**
- Restricting forward reads to `l2Book-fast` and `trades` is right.
- So is a 1-to-1 pack per raw file that never touches `ws`. The skippable frames keep `zstd -dc` output pure JSONL.
- Pinning each frame's `(comp_off, comp_len, comp_sha256)` from the capture, rather than from the pack's own table, closes TOCTOU.
- Reconstruction through `_order` proves, against `raw_jsonl_sha256` and `total_lines`, that no line is lost or invented.
- Escaped keys or values (`"coin"`, `"BTC"`) route by the decoded string, and that is consistent provided the packer and the reader decode with the same parser (see F4.2).

### F4.1 (design). "Provably closed" by run-id order is not a proof, so a live file can be packed
- **What breaks.** Condition (b) takes "any file with `<run'> > <run>`" as proof that `<run>` died. But `<run>` is "the run's start, in ms since epoch" (`RECORDER.md`), read from the host clock. That clock steps: `RECORDER.md` itself handles a backward step within a run. A run started under a fast clock gets a larger id than a later run.
- **Construction.**
  - `prodesk7` comes back from a long power-off with its RTC about a minute fast, and `mmrec` starts before chrony's first step. Run A, id = true + 60 s, writes some `l2Book-fast` lines and dies, say because the connection drops at boot.
  - Kubernetes restarts it within its back-off (10 to 40 s). Chrony steps the clock back 60 s in between, so run B gets an id below A's.
  - From then on, every live file of B satisfies (b), because A's file has a larger run id, and does so for B's whole life (weeks).
  - The packing job, which runs "as hours close", packs B's live hour at whatever `L_raw` it snapshots. Two hosts agree on that prefix.
  - `Capture_k` then pins the pack. The replay reads the hour truncated, while the raw file goes on growing.
- **Outcome.** One of two things happens, and both are bad:
  - Every replay reads holes the record does not have: staleness, in which nothing fills. They agree month to month, so nothing flags it. This is a lost recording, as far as the judged record is concerned.
  - Or the next capture's check `stat(f).size == L_prev` on the packed raw fails closed. With F2.1 that stalls the study for good.
- **Fix, at the cause.** Delete clause (b). Its other half, "a later hour of `<run>`", already implies (a), since a run ends a file's stream at rollover. A run's death cannot be read from clock-ordered names. A cut file is then simply read raw: one file per crash, about 75 MB, already re-hashed each capture as "open (cut)". If packing cut files ever matters, order runs by a counter persisted on `ws`, not by a clock.

### F4.2 (design). Packed ≡ raw is load-bearing for the study's survival, and three points of it are unspecified
- **What breaks.** A closed hour not yet packed at a capture is read raw, and at a later capture it is read packed. If the packing host lags, as one on "this PC" will when it is off, that hour can be one already published. Then any difference in what the two representations feed goes through the prefix check, which reads it as "the record of a published day has changed" and ends the study. Test 14's equivalence on synthetic data is the only guard. Three points are open:
  1. **A3's tie order for `_other`.** Equal `(time, class, coin, kind, source)` keep "their position in their source". A coin's events split between frame `c` and `_other` (a mixed-coin `trades` array, a schema change mid-hour) have no recoverable relative position, because the replay never reads `_order`. A reader that feeds `_other` after the frame differs from a raw read at ties.
  2. **What the raw reader does with a non-universe line.** If the raw reader validates a line fully before skipping it (a garbled `levels` of coin `FOO`), raw reading rejects a record that packed reading never sees, since frame `FOO` is unread. The same holds for counts taken over all coins.
  3. **A deterministic misroute.** Two hosts running one frozen packer agree on its mistakes. A universe line routed into a non-universe frame passes reconstruction and passes two-host comparison, and purity is checked only on frames that are read. The report's "closes misrouting attacks" covers host faults, not packer defects.
- **Construction (1).** A `trades` line `[{"coin":"BTC",…,"time":t},{"coin":"ETH",…,"time":t}]` sits beside a BTC print of the same `t` in frame `BTC`. Read raw at capture `k`; read packed at `k+1`, after the packer catches up. The trace's order at `t` differs, and the study ends at the day before `t`.
- **Outcome.** A judged record ends early on a day whose record never changed.
- **Fix, at the cause.** Make equivalence true by construction, not by test:
  - one attribution function in the build decides a line's coin for the packer and for the raw reader, and the raw reader skips a non-universe line unread;
  - the packed reader merges `_other` by `_order` whenever `_other` holds an event of a universe coin, since `_order` is small;
  - `unpack-verify` checks purity on every frame, not only on frames read.

  Independently, forbid the switch: `Capture_k` does not pin any closed hour before the previous horizon raw if it can wait for its pack. The capture waits, which only lengthens `D` and defers days.

### Note N4.1. The protected window at the pack's edge
Deciding `R_PROTECTED` from "any event timestamp" means `mm2 pack` decodes the boundary files' protected lines, for example `20270131/00` holding events stamped `2027-01-30T23:59:59.9`. The refusal must carry the file name only: no line, no timestamp, no count. Otherwise the status channel leaks a fact derived from the window. With F3.1's fix (no capture while a read date is protected), the forward reader's out-of-horizon counts can never count protected events either.

### Note N4.2. A lost pack need not halt the study
A pack is a deterministic function of the raw bytes (single-threaded zstd, pinned version and level). Re-packing reproduces the pinned bytes, so it should count as the "byte-identical mirror" that `halt_storage_corrupt` asks for. Packs are never overwritten.

## 5. D217: float windows as a two-stack queue with Chan's formula

**What I accept.**
- With no subtraction, an evicted value leaves no trace, which fixes stage 6's defect 1.
- The centred `m2` fixes defect 2.
- The algorithm is specified to the bit (flip schedule, `combine`'s parenthesization, the fallback, the query), so two faithful implementations agree.
- `NaN` cannot arise in `m2`: no subtraction, and `k_a·w > 0`. `μ` stays finite. `s` may become `±∞` or `NaN` (`∞ + −∞`), which `N.keep` maps to `none`.
- `frontGoodLen` is right at both edges: a `none` at evicted index 0 is never combined, and a `none` newest in `front` keeps every front suffix bad until it leaves.
- None of the twelve rewrite rules touches a window (`Rewrite.lean`), and L3 and N1 compare runs with the same tick schedule, so the split's phase breaks neither.

I simulated the stated algorithm in binary64 (Appendix A; the window `n`, preceded by `p` zeros).

### F5.1 (text, and the case against stage 6). The split's effect is not "O(1)-ULP": defect 3 is still there
- **What breaks.** The report says the split "introduces deterministic O(1)-ULP parenthesization differences". With cancellation or overflow it changes the result by up to 100%, or changes whether there is one. The same last `n` values give:

  | window | `p` (phase) | `sum` | `mean` |
  |---|---|---|---|
  | `[1.0, 1e20, −1e20]`, `n = 3` | 0, 2, 4 | 0.0 | 0.0 |
  | | 1, 3, 5 | 1.0 | 0.333… |
  | `[1e16, 1, 1, −1e16]`, `n = 4` | by phase | 0.0 or 2.0 | 0.0 or 0.5 |
  | `[1e308, 1e308, −1e308, −1e308]`, `n = 4` | 2, 4, 7 | 0.0 | |
  | | other phases | `none` | |

  Even without cancellation, the bound on the spread across splits grows with `n`, not as O(1) ULP. So the output still depends on the stream's history before the window, which is stage 6's defect 3, cited as one of three reasons to leave stage 6. `kernel-v2.md`'s "every float operation's result is the one binary64 its arguments determine" is false for windows unless "arguments" means the whole history.
- **Outcome.** No judged result of study 2 changes. Each replay starts at `w_start`, so the phase is the same in every replay, and the ladder reads no float window. It would matter only if step 3's trigger reads `sum`, `mean` or `std` near cancellation. Even then the replays agree, and only the spec's description is wrong.
- **What to do.** Correct the text: the window is a deterministic function of the node's input sequence from its first tick, and defects 1 and 2 are fixed, not defect 3. If locality is wanted, the cost argument against exactness is overstated:
  - an exact sliding sum of binary64 values needs a fixed ~2,100-bit accumulator (about 33 words) with exact add and subtract, which is O(1) per tick with no GMP;
  - the correctly rounded sum and mean then follow from one rounding;
  - `std` needs a ~4,200-bit `sumsq` and an exact square root of a rational.

  The real obstacle is `NumOps α` parametricity, not speed. That is the architect's choice. This note asks only that the stated reason be the true one.

### F5.2 (process). B4's window half is not independent unless the plan makes it so
- **What breaks.** B4 part 2 compares the kernel's new windows with a reference changed by "only" the same new rule. If one builder writes both, B4 part 2 checks one reading of A17 twice. The oracle meant to catch that cannot do so as written:
  - an "exact-rational two-pass oracle" cannot be bit-identical to a rounding algorithm;
  - step 5a's test 2 uses "within `1e-12`" and "matching", against D198's "zero tolerance".
- **Outcome.** For any study whose judged program reads `sum`, `mean` or `std`, a shared misreading could pass B4. Study 2 is affected only if step 3's trigger reads them.
- **Fix.** The reference's windows are written by another model, from A17's text alone, without reading `Eval.lean` (`CLAUDE.md`, Correctness). The oracle is used bit for bit where binary64 is exact: small integers and dyadics with `|Σ| < 2⁵³`. That checks the queue's mechanics (eviction, `none`, `n = 1`, flips) independently of rounding. Rounding cases are given as hand-derived bit patterns, with no tolerance anywhere.

### Note N5.1. Signed zero
"Exact on every constant window" fails for `−0.0`: `mean([−0, −0]) = +0` while `sum = −0`, because `δ = +0` and `μ = −0 + (+0)·w = +0`. It reaches no outcome, but the claim and test 2's list should say so.

### Note N5.2. Stale plan for B4's v2 reference, and test 3 confounded

## Appendix A: the window simulation (binary64, Python floats)

```python
import math
E=('empty',)
def bad(k): return ('bad',k)
def good(k,s,mu,m2): return ('good',k,s,mu,m2)
def ofOpt(x): return bad(1) if x is None else good(1,x,x,0.0)
def kk(a): return 0 if a[0]=='empty' else a[1]
def combine(a,b):                         # older a, newer b; A17 as round 8 states it
    if a[0]=='empty': return b
    if b[0]=='empty': return a
    if a[0]=='bad' or b[0]=='bad': return bad(kk(a)+kk(b))
    _,ka,sa,ma,qa=a; _,kb,sb,mb,qb=b
    k=ka+kb; s=sa+sb; d=mb-ma; w=float(kb)/float(k)
    mu = ma+d*w if math.isfinite(d) else (float(ka)/float(k))*ma + w*mb
    return good(k,s,mu,(qa+qb)+(d*d)*(float(ka)*w))
class W:
    def __init__(s,n): s.n=n; s.front=[]; s.back=[]; s.bagg=E
    def push(s,x):
        s.back.append(x); s.bagg=combine(s.bagg,ofOpt(x))
        if len(s.front)+len(s.back)>s.n:
            if not s.front:
                acc=E
                for i in range(len(s.back)-1,0,-1):
                    acc=combine(ofOpt(s.back[i]),acc); s.front.append(acc)
                s.back=[]; s.bagg=E
            else: s.front.pop()
    def q(s):
        if len(s.front)+len(s.back)<s.n: return None
        a=combine(s.front[-1] if s.front else E, s.bagg)
        if a[0]!='good': return None
        keep=lambda v: v if math.isfinite(v) else None
        return keep(a[2]), keep(a[3]), keep(math.sqrt(a[4]/s.n))
def run(n,window,pre):
    w=W(n)
    for x in [0.0]*pre+window: w.push(x)
    return w.q()                           # (sum, mean, std) for the same last-n values
# run(3,[1.0,1e20,-1e20],p): sum 0.0 at p=0,2,4 and 1.0 at p=1,3,5
# run(4,[1e308,1e308,-1e308,-1e308],p): sum None at p=0,1,3,5,6 and 0.0 at p=2,4,7
# run(2,[-0.0,-0.0],p): sum -0.0, mean +0.0
```
