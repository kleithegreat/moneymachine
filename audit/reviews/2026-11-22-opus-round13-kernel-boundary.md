## Findings

### 1. The policy literal binds a file, not the constant `windows` reads (design; built)

**What it breaks.** "The policy's bytes are a literal the check writes" (B2; sub-step 1). The check writes `Engine/PolicyText.lean` and refuses a library *file* of that name, but nothing requires that the constant `Engine.Machine.policyText` the build ends up with is that module's, or that any module imports `Engine.PolicyText`; and the frozen print shows `policyText` by its type alone. So `Engine/Policy.lean` may keep `def policyText : String := "…"` with any windows and leave the generated module unimported: every clause passes.

**Construction** (`~/.cache/mm-r13k-review/policy/`, built on the pinned toolchain). Step 5's `Json.lean`, `Windows.lean` and `Policy.lean` in two trees, each with the generated `Engine/PolicyText.lean` (written by `String.quote` as the check would). *honest* imports it; *shadow* does not and declares `policyText` itself as the forward window with a one-day hole, [2026-11-01, 2026-12-16) and [2026-12-17, 2027-01-31). Results: every kind and key of the shadow files is on `b94e128`'s survey (`shadow.survey`, round 12's prototype), and its atoms are step 5's `Policy.lean`'s less `include_str`; `policy_is_data` proves in both; a stand-in for the frozen print of `windows`'s closure (Init by name, `policyText` by type, the rest in full, `Probe.lean`) is byte-identical across the two (265 lines, SHA-256 `d37081ca…`); the compiled `windows` is the file's window in *honest* and the two windows in *shadow*; `policyText` is declared in `Engine.Policy` there, and `Engine.PolicyText` is never built. Step 5's `protected_test.ml` probes only the window's edges and two events in it, so by reading it passes too (not run). The same holds with no malice: a stale literal kept by a builder silently drops every window a later commit adds.

**Outcome.** A leak: the engine admits events inside the forward confirmation window (the hole) into reports and traces that research reads, contrary to A13 and the Holdout rule, and selection on them would contaminate CS2.1 to CS2.3's confirmation. `study2 forward` asserts its compiled windows' hash against `Capture_k`'s (D225), which would stop the forward runs if that hash is of the engine's windows, but no check guards `mm2` runs.

**Fix (design, small).** Bind the constant, not the file: after the build, require `Engine.Machine.policyText` to be a definition whose value is the string literal of the file's bytes. That alone suffices, since `windows`'s full print already pins that it reads exactly that constant. Add a fixture `PolicyShadow` (this construction).

### 2. An import "under `Engine`" can name a file outside `Engine/`, or a second name for one file (hygiene; built; no outcome found)

**What it breaks.** "An import names `Engine` or a module under it" is a test of names, while Lake and the check resolve paths with `modToFilePath`, which joins components verbatim. Built (`~/.cache/mm-r13k-review/dotdot/`): `import Engine.«.».Alias` builds module `Engine.«.».Alias` from `Engine/Alias.lean`; `import Engine.«..».Outside` builds `Outside.lean` at the tree's root, its `.olean` at `.lake/build/lib/lean/Outside.olean`. `Engine.«..».Init.Shadow` fails the build: Lake gives `lean` `LEAN_PATH` with the build's library ahead of the toolchain's (`Lean/Util/Path.lean:61,108`), and the `Init` directory the module's output creates there leaves `Init` unresolvable. So shadowing `Init` this way fails closed.

**Outcome.** None found: the check and Lake map a name to the same path, so the bytes built are the bytes checked, and a `..` name only moves a file the check wrote. But "a library file of that name" (`Engine.PolicyText`) is decided by name, which `Engine.«.».PolicyText` evades, and "a fresh directory" stops holding everything. Noted, not a blocker: requiring each import component to be a plain identifier (no `.`, `..`, separator or empty part) removes the question at one line's cost, with a fixture `DotComponent`.

### 3. The toolchain reading is right, but its text overstates and under-lists (text)

- **"Runs none of the library's code" means compiled code.** The kernel and `Meta.whnf` reduce library definitions by design (`decide +kernel`, `policy_is_data`, the laws' witnesses running `parse` and `start`). That is evaluation in the logic, with no effects, and the claim survives once worded that way.
- **The list of `evalConst` sites is incomplete.** Grepping 4.34.0's `src/lean/Lean` also finds sites the report does not name: linters' attribute handlers (`Linter/UnusedVariables.lean:143`, `MissingDocs.lean:43`, `EnvLinter/Basic.lean:59`, `CodeQuality/Frontend.lean:46`), compiler folders and passes registered by attribute (`Compiler/LCNF/Simp/ConstantFold.lean:648`, `LCNF/PassManager.lean`), parser, formatter and attribute registrations (`Parser/Extension.lean`, `PrettyPrinter/Basic.lean:27`, `Attributes.lean:450`), markdown renderers and deferred doc checks (`DocString/Markdown.lean:548`, `Elab/DocString/Builtin/Postponed.lean:87`), widgets and library suggestions. Two more are triggered by `autoParam`: pretty-printing an `autoParam` type (`PrettyPrinter/Delaborator/Builtins.lean:1545`) and `#print` (`Elab/Print.lean:156`). Each is reached by an attribute or command off the list, or by `autoParam`, so the three-way classification holds.
- **`native_decide` no longer uses `Lean.ofReduceBool` in 4.34.0.** `Meta/Native.lean:37–90` evaluates an auxiliary constant with `evalConst` and adds an axiom `_native…ax`. It is reached by `native_decide`, `decide +native` and `bv_decide`, all forms or keys off the list, and the axiom clause would also reject it. The "kernel's native reduction" route remains only through `Lean.reduceBool`/`reduceNat` (`Meta/WHNF.lean:981–987`, `Meta/ExprDefEq.lean:195`, the kernel).
- **The environment.** The derivation should run the check and Lake with `LEAN_PATH`, `LEAN_SYSROOT` and Lake's cache variables unset, since an inherited `LEAN_PATH` entry precedes the toolchain for both. "`Init` is the pinned store path both use" holds only then.

## What I confirm

- **Three entry points.** The first is `evalConst`, including `[init]` declarations, which `Compiler/InitAttr.lean:157–196` runs through `evalConst`/`runInit`. The second is the kernel's reduction of `Lean.reduceBool`/`reduceNat`. The third is native initializers, which run only for libraries the `--setup` file loads; their `dynlibs` and `plugins` come from the pinned lakefile, which has none (`Lake/Build/Actions.lean:29–63`). An `[init]` entry needs the `initialize` commands, off the list, or the `init` attribute, which the attribute keys refuse wherever it sits (on a `let rec` or `where` its kinds are off the list as well).
- **The triggers are syntactic.** An auto-param is `isAppOfArity ``autoParam 2` on the parameter's type with a constant tactic (`Elab/App.lean:826–829`, `Expr.lean:1702`). Native reduction is `.app (.const ``Lean.reduceBool) (.const c)`. No `Init` definition wraps either around a parameter: `autoParam` occurs in `Init` only at its definition (`Tactics.lean:2653`) and in two `simp [autoParam]` calls. Every `Init` `export` that could alias a `Lean` constant sits inside `namespace Lean` (`Prelude.lean:5588,5652,6063`; `Meta/Defs.lean:365,459,1409`). Values under `Lean` remain reachable without the name (`"x".toName : Lean.Name`, built), but no listed form evaluates a value. So the name rule closes both triggers, and I found no other spelling, alias, unfolding, instance or field default that reaches them.
- **The listed tactics run nothing of the library's.** `decide +kernel` goes to the kernel alone (`Elab/Tactic/Decide.lean`, `doKernel`), and `kernel` is a field of `DecideConfig` only (`Init/Tactics.lean:1388`). `simp`'s and `grind`'s `evalExprWithElab` serve `(config := …)` and valued items (`Elab/Tactic/Simp.lean:77,91`; `Grind/Config.lean:36,52`), which the keys refuse. `simp` evaluates declared simprocs only (`Simp/Simproc.lean:59–77`), and the library can declare none. No `Init` macro behind a listed kind expands to an evaluating form.
- **The check and `lean` parse alike.** The library adds no syntax, opens only `Engine` namespaces (so no scoped syntax), and cannot set `doc.verso`, which switches the docstring parser (`DocString/Parser.lean:1373`, default false).
- **Lake needs nothing beyond the tree and the pinned lakefile.** In my builds it wrote its own manifest ("no previous manifest, creating one from scratch") and built with no `lean-toolchain` ("no toolchain information found").
- **The compiled engine holds no world.** In 4.34.0 `IO.RealWorld` and `Void` are opaque nonempty types (`Init/System/IO.lean:26–31`, `Init/System/ST.lean:15–23`), and `Void.mk` needs a world. `opaque w : IO.RealWorld` is noncomputable (built: "depends on `Classical.ofNonempty`"), and `sorryAx` falls to the axiom clause. So the deleted purity argument is needed neither during the build nor at run time.
- **Export names cannot smuggle C.** The toolchain refuses an `@[export]` name that is not a C identifier (`Compiler/ExportAttr.lean:15–21,60`), so a key beginning `mm2_` carries nothing else.
- **The boundary fails closed.** Forms, atoms and keys fail closed. The name rule is a deny rule, complete relative to this reading of 4.34.0, which B2 already requires redoing whenever `flake.lock` moves. No listed form or admitted name defeated it. The one route I found (finding 1) bypasses the forms altogether: a value the frozen print does not show.
