# Review: what a C4.5 v3 should count, if one is needed

Consultant review, read only. Clock at time of reading: 2026-11-02 03:18 UTC (2026-11-01 22:18 EST). Nothing was edited.

## Summary

The only false-discovery quantity a complete-null test measures is the share of campaigns that promote something (`docs/whitepaper.tex:546`). v1 and v2 both judge a different count: promotions plus behaviour failures that are imputed as promotions. v1 and v2 did not fail on a false discovery, and v2 cannot either. They failed, or will fail, on the imputations. Across 8 swarm campaigns so far there have been zero real promotions, zero finalists and zero screened candidates.

A v3 should judge two things and keep them apart:

- **False promotions.** Count every observed promotion. Also impute a promotion wherever the outcome is missing and the reason it is missing could depend on the data.
- **Establishment.** Did the procedure actually run end to end? This is a per-campaign check of data-path facts. It is never a floor on how much the agents did.

The verdict has one pass and two labelled failures. Keep the harness and the brief unchanged. Write the v3 text before v2's last four campaigns finish.

## 1. What this test can and cannot establish

**F1. A pass is guaranteed by theory, given four assumptions; the 10 runs test those assumptions.** The holdout's betting test holds for any choice made using search-period information only (`whitepaper.tex:340-347`, criteria.md:164). On a null market the holdout is fresh noise, so P(false promotion) ≤ α for any way the agents search, provided four things hold:
1. nothing from the holdout leaks into search;
2. the test and gate are implemented correctly;
3. no evaluation goes bankrupt (`gate/NULLS.md`, "No edge");
4. the per-step loss cap holds.

So C4.5 can only detect a broken assumption on the swarm's own code paths: the history channel, a multi-agent ledger, freeze → batch. It cannot establish anything about mixed-market FDR, power, or how agents search on real data. On noise they stop after 5–17 evaluations; near real structure they may search harder.
*Could change:* how a pass is worded. "C4.5 met" must not be read as validating swarm error control.

**F2. The judged outcome is almost insensitive.** Under C2.4, every baseline searcher promoted 0 of 300 on the complete null, and 0 of 300 had SPA rejecting with finalists (`audit/stage2/exit-r2.md:13`). H400's screened count never exceeded 0 in 300 N2 runs (`null-summary-v1.json:154`). Every swarm campaign so far has screened 0.

With "at most 1 of 10" as the threshold, P(fail) is:

| True per-campaign rate | P(≥ 2 of 10), i.e. fail |
|---|---|
| 0.01 (the baseline's bound) | ≈ 0.004 |
| 0.1 | ≈ 0.26 |
| 0.3 | ≈ 0.85 |

So the test only catches gross breakage, such as a leak. Search intensity barely moves this. Even 400 evaluations would not make promotions likely, because the screen and the betting test sit in between.
*Could change:* every argument about evaluation counts. They hardly affect the false-discovery outcome, which is why v1's floor added failure modes without adding any ability to detect a false discovery.

**F3. A count of 10 bounds the rate only loosely.** Exact one-sided 95% upper bounds: 0 of 10 → 0.26; 1 of 10 → 0.39; 2 of 10 → 0.51. The bound assumes independent, identically behaving campaigns. That holds while agents have no memory across campaigns (decisions.md 2026-11-02 01:44 UTC (2026-11-01 20:44 EST)). It breaks if the memory research question is ever folded in.
*Could change:* what the result may claim, and whether the memory study needs its own null design (it does).

## 2. Which failed or partial campaigns must still count

**F4. Rule: impute a promotion when the outcome is missing and the reason could depend on the data. Otherwise the campaign is "not established", not counted.**

This is the standard distinction in missing-data statistics. Data that is missing for reasons unrelated to the outcome (missing at random) can be set aside. When the reason for missingness can depend on the outcome (informative censoring, "missing not at random"), you take the worst case, which here means imputing a promotion. The project already applies this rule implicitly in one place: a real attempt with zero evaluations is void because "nothing from the data reached the agent … so it opens no selection channel" (criteria.md:369).

v3 can decide "could depend on the data" mechanically from the append-only ledger: did the censored entity receive any eval or history disclosure before the censoring event? Applied case by case:

| Case | Data seen first? | Treatment |
|---|---|---|
| Any promotion, whatever else happened (crash, audit failure, …) | n/a | **Counts.** Nothing can void it. |
| Gate, freeze or holdout decision did not complete; ledger missing; daemon calls that don't match ledger rows | yes | **Counts (imputed).** The outcome is censored exactly where a promotion is decided. Those paths run most often when finalists exist, so the censoring is informative. |
| Kernel `abort` on an evaluation (row_kind, campaigns.py:59-66), e.g. I5 at high equity | yes | **Counts (imputed) if the abort followed equity growth.** A compounding strategy is exactly the one the screen would rank first. Otherwise report it. |
| A session that crashed **after** disclosures, with the gate completed over the ledger | yes | Observed outcome stands. Campaign is **not established** (search was cut short, and the cause, e.g. a long session hitting account exhaustion, may track promising results). |
| An agent that saw nothing (no eval, no history reply) and then stopped or crashed, like N2-5's A4 (`swarm-null-2-so-far.jsonl` row 6: spent 0, history_calls 0) | no | **Non-informative.** Report it. The campaign is established if the rest holds. |
| No agent made any evaluation | no | **Not established.** The test was vacuous. |

Under this rule, N2-5 is an established campaign with 0 promotions. v2 counts it as a promotion (criteria.md:474; `counts`, campaigns.py:131-134), and its record carries `counts_as_promotion: true` next to `promoted: []`.
*Could change:* v3's pass/fail, and the meaning of the summary's `counted_promotions` (campaigns.py:543).

**F5. The "conservative" direction depends on the test.** For the real campaign, a missing finalist counts as p = 1, i.e. not promoted (criteria.md:402), which is conservative there. In a null test, conservative means imputing a promotion. The paper's amendment rule ("only if the change cannot increase false discoveries", `whitepaper.tex:540`) lets any imputation in the false-discovery direction through. That is how v1's floor and v2's per-agent rule were both admitted, even though neither event can hide a false discovery (decisions.md:424 says this of C3.2 v3's identical tightening).

A one-sentence companion beside the amendment rule would close this: "In a null test, a missing outcome counts as a promotion only when its absence could depend on the data; any other failure means the test was not established." That one sentence explains criteria.md:369, :396, :402 and :474, rather than each restating its own rule.
*Could change:* whether a v4 repeats this pattern. A paper change requires the rebuilt PDF and a Blockers note first (CLAUDE.md §3).

**F6. Survivorship.** v3 must keep fixed ids with every started campaign counted, and no replacement, padding or retry (as criteria.md:474 already does). It may stop early only once the verdict is fully determined. A "not established" series is not a free retry. Under the paper, only the human can authorize a new version (`whitepaper.tex:540`).

There is also survivorship across versions. v1, v2 and a v3 would each have been rewritten after a failure that was not a false discovery, which is a garden of forking paths on the criterion. It cannot hide a false discovery today, because none has occurred. It should still be stated (see F11).
*Could change:* whether a pass is credible to an outside reader.

**F7. One agent's exception throws away the whole campaign's gate decision.** If `run_agent` raises (for example, `disclose`'s `check=True` at harness.py:44), `list(pool.map(...))` re-raises (harness.py:54-56). The executor's shutdown waits for the other agents first, so the ledger is complete, but `run_series` records `{"crash": …, "counts_as_promotion": True}` without running the gate (campaigns.py:279-283).

C3.3's revision already holds that "the gate's steps … are functions of the ledger" (criteria.md:401). For v3, `swarm_null` should catch the exception and still run the gate over the ledger. That edit sits in campaigns.py, which is outside `harness_hash` (harness.py:29), so it is not a fork. It must not touch v2 while v2 runs.
*Could change:* an infrastructure accident being recorded as a promotion instead of the outcome actually observed.

## 3. Non-vacuity without repeating v1's mistake

**F8. Require that the data paths ran, not that agents did a certain amount.** v1's 200 floor and v2's per-agent rule made the same mistake: they required behaviour the registered procedure does not guarantee (criteria.md:475 says this about the floor), then counted its absence as a false discovery.

What the false-discovery claim depends on is that these paths actually ran:
- the gate decided over an audited ledger (C3.1/C4.3 match) with at least one filled trial, so SPA and the screen executed;
- cross-agent history was delivered (C4.3's last bullet, criteria.md:463);
- the holdout decision step completed.

A campaign is **established** when all of these hold and no session crashed after seeing data. No evaluation count enters it.

One caveat: C4.3's last bullet is itself a behaviour requirement. It holds only if agents call `history`, which they did 0 to 7 times each. It has held in all 8 campaigns, but it is the next place a v1-style failure can occur. It currently fails the stage per campaign, not per series.
*Could change:* whether a working swarm in which one agent misuses its tool can pass, and whether C4.3 needs the same treatment later.

## 4. A three-way outcome

**F9. Warranted, as one pass and two labelled failures, not as a new kind of result.**
- **Pass:** all ten recorded, at most 1 false promotion (observed plus imputed), and at most 1 campaign not established.
- **Failed, false discoveries:** 2 or more false promotions. This dominates the other label.
- **Failed, not established:** anything else.

Both failures have the same consequence: the stage does not exit, the record stays, and a further version needs the human and fresh ids. Only the label differs.

The project already needed the second label once, ad hoc: C3.2 v2 "established no procedure" while reading 1 of 20 (criteria.md:395). v3 then folded "not established" into the promotion count (criteria.md:396), and that merger is what N2-5 tripped. The value of splitting them is that the audit record stops reporting promotions that did not happen.
*Could change:* the stage 4 report's wording, and whether a future failure is read as evidence about false discoveries.

## 5. What to judge and what to report

**F10. Judge only false promotions and establishment, plus C4.3 as it stands.** Report the rest beside fixed reference distributions written down before any v3 run:
- per-campaign SPA p-value, max DSR, screened count and finalists at each N (C4.4), beside H400's 300 runs and C3.2 v3's 20 single-agent campaigns;
- **finalists under the null.** This is the most informative number here. Every finalist on a null market is a false selection, and C2.4's second bullet judged baselines on it (criteria.md:269). Even so, it is a selection-efficiency property the paper does not claim for swarms (`whitepaper.tex:331`, :552), so judging it would repeat the category error of judging something other than promotions. Report it, with a pre-written statement that 2 or more campaigns of 10 with finalists would be far outside the baselines (0 of 300);
- bankrupt evaluations (no edge is claimed only without bankruptcy, `gate/NULLS.md`), and aborts with their causes;
- **denials by kind, including sandbox-escape attempts.** A4 set `dangerouslyDisableSandbox` (decisions.md:506). Leakage is the only route by which a swarm could beat F1's guarantee, and C3.1 records denials without failing on them (decisions.md 2026-10-31 23:12 UTC (19:12 EDT));
- per-agent evaluations, history calls and stop causes, and agents that saw no data (so far 1 of 24);
- observed promotions pooled across every version with the same harness hash, kernel and N2, with the exact bound (F11).

*Could change:* nothing judged. It changes what a reader can learn from 10 campaigns.

## 6. Harness or brief change

**F11. None.** Allowing `/work/mm-agent` (session.py:40) or adding a line to the brief changes `harness_hash` (harness.py:29-31). That forks the stage 3 identity (criteria.md:356): C3.2's evidence would no longer cover the harness, and every swarm null would need fresh ids. The benefit would be operational reliability for 1 agent in 24. Under F4, that agent is non-informative and does not affect the false-discovery outcome.

A brief edit also changes agent behaviour in ways nobody has measured, and patching a refusal that worked as designed is the kind of patch-around CLAUDE.md §1 forbids. If a fork happens anyway (the Lean engine stage, or the memory study), fold the absolute-path form into it then.
*Could change:* whether stage 3's calibration still covers the frozen harness.

## 7. What must be fresh

**F12.**
- **Judge v3 on fresh ids only** (e.g. `swarm-null-3-N2-0..9`), with the harness, brief, kernel, N2 and gate unchanged. The changes are confined to campaigns.py's counting and recording.
- **Reusable as references** (not judged by C4.5): H400's C2.4 runs, C3.2 v3's 20 campaigns, and the locked holdout suite.
- **Pooled report.** v1, v2 and v3 ran the same procedure under different counting rules, so their observed promotions are interchangeable draws. Report them pooled, e.g. "0 observed in 22 campaigns, 95% bound 0.13". Do not judge on the pooled figure, since v3 would be written after seeing v1 and v2.
- **Timing.** If v3 is to be the fallback, write its text into a decision record now, before v2's remaining four campaigns finish, so that how v2 ends cannot shape it. Do not touch v2: if it ends at 1 counted of 10, it passes as written, and the report should say its one count was not a promotion.

*Could change:* whether v3's pass is credible as evidence produced after its criterion.

## 8. What is wrong with this recommendation

1. **It loosens v2 after seeing a failure.** A dead agent no longer counts, and a crash after the gate has run is no longer imputed. To a skeptic, v1 → v2 → v3 each look like a rule rewritten until it passes. Fresh ids and the pooled report limit the damage; they do not remove the appearance. Because this loosens a frozen rule, it is the human's call.
2. **The "could depend on the data" predicate adds a place for judgement.** That is only safe if code computes it from ledger rows, with missing evidence defaulting to "imputed". An advisor arguing after the fact that a crash "was data-independent" would reopen the hole.
3. **The cap of 1 non-established campaign is arbitrary.** It mirrors the false-discovery threshold rather than following from anything.
4. **Leaving finalists unjudged leaves the only sensitive number unjudged.** Given F2, a pass will mostly certify plumbing. The C2.4 precedent supports the opposite choice, judging finalists, if the human prefers a test that can fail on something swarm-specific.
5. **Tolerating dead agents validates the swarm as it actually ran.** If tool misuse is frequent in a real campaign, the real swarm is weaker. That is a power issue the null test will not flag, not a false-discovery issue.
6. **It may be moot.** If v2 ends at 1 of 10, no v3 runs, and the drafting effort only buys a cleaner record and a pre-commitment. CLAUDE.md gives no review rounds to work that isn't active, so keep the v3 draft to one decision paragraph until v2 fails.
